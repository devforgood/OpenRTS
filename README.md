# OpenRTS

.NET 서버와 Unity 클라이언트로 만드는 오픈소스 RTS 프로젝트입니다.
서버 구조는 LeagueSandbox GameServer(LoL 4.20 서버 에뮬레이터)를 분석한 내용을 참고하지만, **코드는 가져오지 않고 새로 작성합니다** (아래 [라이선스 검토](#2-참고-자료-라이선스-검토) 참고).

개발에 참여한다면 [개발 문서(docs/)](docs/README.md)부터 읽으세요: 개발 환경·코드 규칙, 아키텍처와 틱 순서, 프로토콜 형식, 시뮬레이션 규칙, 클라이언트 구성, 테스트 방법.

---

## 1. 저장소 구성

```text
OpenRTS/
├─ Shared/                         서버·클라이언트 공용 코드 (어느 쪽에도 속하지 않음)
│  ├─ package.json                 Unity 로컬 패키지 com.openrts.shared
│  ├─ OpenRTS.Shared.csproj        .NET 빌드용 (netstandard2.1, C# 9)
│  └─ Runtime/                     소스 + OpenRTS.Shared.asmdef
├─ Server/                         .NET 11 솔루션 (OpenRTS.slnx)
│  ├─ src/OpenRTS.Server/          게임 서버 콘솔 앱 (net11.0)
│  └─ tests/OpenRTS.Server.Tests/  xUnit 테스트
├─ Client/                         Unity 6 프로젝트 (6000.6.0f1)
│  └─ Assets/Scripts/              클라이언트 코드 (OpenRTS.Client.asmdef → OpenRTS.Shared 참조)
├─ Directory.Build.props           모든 .NET 빌드 출력을 artifacts/ 로 모음
├─ global.json                     .NET SDK 11.0.100 고정 (상위 기능 밴드 허용)
├─ THIRD_PARTY_NOTICES.md          외부 라이브러리 라이선스 고지 (LiteNetLib MIT 등)
└─ docs/                           개발 문서 (아키텍처·프로토콜·시뮬레이션·클라이언트·테스트·개발 규칙)
```

### 공용 코드(Shared) 관리 방식

DLL을 복사하지 않고 **같은 소스를 양쪽에서 컴파일**합니다.

- **서버**: `OpenRTS.Shared.csproj` 를 `ProjectReference` 로 참조합니다.
- **Unity**: `Client/Packages/manifest.json` 에 `"com.openrts.shared": "file:../../Shared"` 로 등록된 로컬 패키지이고, `Runtime/` 의 소스를 asmdef로 직접 컴파일합니다.
- csproj가 **netstandard2.1 / C# 9** 로 고정되어 있어서, Unity가 지원하지 않는 문법이나 API를 쓰면 `dotnet build` 에서 먼저 실패합니다.
- 빌드 출력(`bin/`, `obj/`)이 `Shared/` 안에 생기면 Unity가 그 안의 생성된 `.cs` 까지 컴파일하므로, `Directory.Build.props` 로 저장소 루트의 `artifacts/` 에 출력합니다.
- Shared에는 `UnityEngine` 이나 서버 전용 라이브러리를 참조하지 않는 순수 C#만 둡니다: 프로토콜·메시지 정의, 직렬화, 시뮬레이션 상수, 수학.
- `Shared/` 의 `.meta` 파일은 Unity가 만든 것이며, 에셋 GUID를 유지하려면 커밋해야 합니다.

### 빌드 / 실행

```bash
# 서버 (.NET 11 SDK 필요)
cd Server
dotnet build
dotnet test
dotnet run --project src/OpenRTS.Server -- --port 7777 --bots 3   # Ctrl+C 로 종료
```

클라이언트는 Unity Hub에서 `Client` 폴더를 열고 에디터 버전 **6000.6.0f1** 을 사용합니다.

### 실행과 조작

1. 서버 실행: `dotnet run --project Server/src/OpenRTS.Server`. 접속한 플레이어마다 유닛 8개(설정 가능)를 주고, 배회하는 봇 3개를 만듭니다.
2. Unity에서 `Assets/Scenes/Main.unity` 를 열고 Play 합니다. 어떤 씬이든 `ClientBootstrap` 이 카메라·바닥·벽·네트워크 객체를 만듭니다.
3. 두 번째 클라이언트가 필요하면 메뉴 **OpenRTS → Build Windows Player** 로 `Client/Builds/Windows/OpenRTS.exe` 를 만들어 함께 실행합니다.

유닛 색은 내 팀 기준입니다: 내 유닛 초록(선택하면 발밑에 고리), 같은 팀 파랑, 적 빨강, 중립(전투하지 않는 충돌 확인용 봇) 회색. 원거리 유닛은 긴 총신, 근접 유닛은 짧은 네모 코를 달고, 전투 유닛 머리 위에 체력 막대가 있습니다. 입장하면 내 유닛이 모두 선택된 상태로 시작합니다. 플레이어는 들어온 순서대로 1팀·2팀에 나뉩니다.

### 이동 · 길찾기

- **맵**: 벽은 축 정렬 사각형 목록이고 `Shared/Runtime/Map/MapLayouts.cs` 가 맵 종류(`Open` / `Gate` / `Blocks`)별로 만듭니다. 서버와 클라이언트가 같은 함수를 쓰므로 맵 데이터를 따로 보내지 않고, 설정의 맵 종류만 바꿔 전파합니다.
- **길찾기 격자** (`NavGrid`): 0.5 단위 셀 200×200. 셀마다 가장 가까운 벽까지의 거리(clearance)를 미리 구해 두고, 반지름 r 유닛은 clearance ≥ r 인 셀만 지납니다. 그래서 같은 통로라도 큰 유닛은 못 지나갑니다.
- **A\***: 8방향, 옥타일 휴리스틱, 대각선은 양옆 칸이 모두 열려 있을 때만(모서리 끼임 방지). 직선으로 갈 수 있으면 A\* 를 건너뜁니다. 목표에 갈 수 없으면 도달 가능한 곳 중 목표에 가장 가까운 지점까지 갑니다.
- **경로 단순화**: 셀 경로를 벽과의 정확한 선분-사각형 거리 검사로 줄입니다(string pulling). 이동 중에도 다음 경유점이 직선으로 보이면 지금 경유점을 건너뛰어, 회피로 밀려났을 때 되돌아가지 않습니다.
- **대형**: 여러 유닛에 한 지점을 찍으면 목표를 중심으로 이동 방향을 향한 격자 대형(간격 = 지름 × 1.5)을 만들고, 앞에 있던 유닛을 앞줄에, 줄 안에서는 좌우 순서대로 배정해 서로 엇갈리지 않게 합니다. 모두 같은 점으로 보내면 도착 지점에서 서로 밀치다 막힘 판정으로 멈추기 때문입니다.
- **소유권**: 클라이언트는 유닛 ID 목록과 목표를 보내고, 서버가 그 플레이어 소유 유닛만 골라 움직입니다(남의 유닛 ID 는 무시).

### 충돌 처리 확인

서버는 **RVO2(ORCA)** 로 유닛끼리, 그리고 벽과 피하고, 그래도 남은 겹침은 **분리 보정**으로 밀어냅니다. 벽에 대해서는 마지막에 원-사각형 밀어내기로 한 번 더 막습니다. 설정은 서버가 권위를 가지며, 클라이언트의 **F2 패널**에서 바꾸면 서버에 요청 → 서버가 범위를 검사해 적용 → 모든 클라이언트에 전파됩니다.

| 설정 | 범위 | 기본 | 설명 |
| --- | --- | --- | --- |
| 맵 | Open / Gate / Blocks | Open | 벽 없음 / 가운데 세로 벽에 폭 4 통로 하나 / 사각 장애물 8개. 바꾸면 모든 유닛을 다시 배치 |
| 내 유닛 수 | 1~100 | 8 | 플레이어 한 명이 받는 유닛 수. 바꾸면 플레이어 유닛을 다시 만듦 |

| neighbor dist / max neighbors / time horizon | 1~30 / 1~32 / 0.1~10 | 10 / 10 / 2 | ORCA 파라미터. 시간 지평이 길면 일찍 피하지만 소극적으로 움직임. 벽에 대한 시간 지평은 1초 고정 |

| repath when blocked | on/off | on | 목표에서 먼 곳에서 1초 동안 진척이 없으면, 멈춰 있는 유닛이 차지한 칸에 비용을 얹어 경로를 다시 찾음 (이동 명령당 최대 3회) |
| delta snapshots | on/off | on | 클라이언트가 확인한 스냅샷 대비 바뀐 유닛만 전송. 끄면 매번 전체 (대역폭 비교용) |
| fog of war | on/off | on | 팀 시야 밖 적 유닛을 보내지 않음 (아래 "시야"). 끄면 모두에게 전부 전송 |

멈춘 유닛과 움직이는 유닛 사이에서는 ORCA 회피 몫을 다르게 나눕니다(원본 RVO2 는 항상 반반).

- 지나가는 유닛 ↔ 멈춘 유닛: 멈춘 유닛이 75% 를 맡아 비켜 줍니다.
- 목표 근처에 도착하는 유닛 ↔ 멈춘 유닛: 도착하는 쪽이 전부 맡습니다. 먼저 도착해 자리 잡은 대형 유닛을 밀어내지 않게 하려는 것이고, 분리 보정도 같은 몫으로 나눕니다.

패널 아래쪽에 서버가 2Hz로 보내는 지표가 나옵니다.

- **min separation**: 가장 가까운 두 유닛의 거리 ÷ 반지름 합. 1 이상이면 겹침이 없습니다.
- **overlapping pairs**: 5% 넘게 파고든 쌍의 수
- **blocked stops / repaths**: 막혀서 멈춘 횟수 / 경로를 다시 찾은 횟수
- **wall hits**: 벽에 반지름의 5% 넘게 파고든 유닛 수 (0 이어야 함)
- **server step**: 서버가 한 틱을 처리하는 데 걸린 시간
- **snapshot KB/s**: 클라이언트 한 명에게 보내는 스냅샷 대역폭과 그중 델타 비율

서버 명령줄로 시작 값을 정할 수도 있습니다: `--map gate --bots 50 --scenario pass --player-units 20 --radius 0.5 --speed 6 --no-avoidance --no-repath --no-delta --no-debug-commands` (시나리오는 `battle` 도 가능)

자동 확인: `-autotest-collision <봇 수> <시나리오> [맵]` 으로 실행하면 클라이언트가 설정 변경(내 유닛 1개로 줄임 — 무작위 위치의 내 무리가 봇 경로에 끼면 결과가 흔들려서)을 요청하고, 서버 적용과 전파, 화면 유닛 수, 12초 동안의 최소 간격(0.8 이상)과 벽 침범(0)을 확인합니다.

로드맵 3단계 완료 기준(50유닛이 좁은 길을 겹치거나 튀지 않고 통과)은 `NavigationTests.GatePass50_CrossesNarrowGap_WithoutOverlapOrWallHits` 가 확인합니다. 50유닛 모두 통로를 지나고, 최소 간격 ≥ 0.9, 벽 침범 0, 한 틱 이동량이 최고 속도의 1.5배 이하여야 합니다. 위 표의 "막혀 멈춤" 은 대부분 돌아오는 무리와 늦게 통과하는 무리가 통로에서 마주쳐 생깁니다.

### 스냅샷 대역폭

클라이언트는 다 모은 스냅샷 틱을 서버에 확인 응답(`SnapshotAck`)하고, 서버는 그 틱을 기준(baseline)으로 **바뀐 유닛과 사라진 유닛만** 보냅니다. 기준이 없거나 오래되면(64스냅샷 ≈ 4초) 전체를 보냅니다. 복원은 Unity 클라이언트와 서버 테스트가 같은 `Shared` 코드(`SnapshotReceiver`)로 하고, 통합 테스트가 복원한 상태가 서버가 보낸 양자화 값과 정확히 같은지 확인합니다.

델타는 **필드 묶음 단위**입니다. 항목마다 어떤 묶음이 실렸는지 1바이트로 표시하고, 바뀐 묶음만 보냅니다(4단계에서 체력·공격 대상이 들어오며 바꿈 — "변경분 스탯 복제").

| 묶음 | 내용 | 크기 |
| --- | --- | --- |
| 공통 | 유닛 ID + 묶음 표시 | 3 |
| Position | x, y (16비트 양자화) | 4 |
| Info | 소유자, 팀, 종류 (거의 안 바뀜) | 3 |
| Health | 체력 비율 (1/255) | 1 |
| Action | 공격 대상, 상태 플래그(선딜 중) | 3 |
| Removed | 사라진 유닛 (공통만) | 0 |

움직이기만 하는 유닛은 7바이트, 서서 싸우며 맞는 유닛은 4~7바이트, 새 유닛은 14바이트입니다.

### 전투

로드맵 4단계. 참고 서버의 AI 구조(`ai.md`)를 따라 **엔진 층**과 **행동 층**으로 나눴고, 코드는 새로 작성했습니다(참고 서버는 AGPL).

| 층 | 역할 | 이 프로젝트 | 참고 서버 |
| --- | --- | --- | --- |
| 엔진 | 명령(Idle / Move / AttackMove / Attack)과 대상을 보고 획득·추적·선딜·타격·투사체·사망·도움 요청 처리 | `Simulation/Combat/CombatSystem.cs` | `ObjAIBase.UpdateTarget` |
| 행동 | 누구와 싸울지, 어디로 갈지 명령만 바꿈 | `Simulation/Combat/BattleAi.cs` (전투 봇) | `IAIScript` (`LaneMinionAI` 등) |

| 종류 | 체력 | 피해 | 사거리 | 쿨다운 | 선딜 | 획득 거리 | 시야 | 투사체 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 근접 | 120 | 12 | 0.3 | 1.0초 | 0.25초 | 8 | 10 | 즉시 타격 |
| 원거리 | 70 | 9 | 6 | 1.25초 | 0.3초 | 9 | 11 | 속도 18, 대상을 따라감 (대상이 먼저 죽으면 사라짐) |

수치는 `Shared/Runtime/Combat/UnitArchetypes.cs` 에 있고 거리는 가장자리 사이 기준입니다. 팀 0 은 중립(전투 안 함), 1 이상끼리 팀이 다르면 적입니다.

- **명령별 동작**
  - **Idle**: 획득 거리 안에 적이 오면 스스로 싸웁니다. 싸우기 시작한 자리에서 10 넘게 쫓아가면 포기하고 돌아옵니다(리쉬, 참고 서버의 정글 몬스터 복귀와 비슷).
  - **Move**: 적을 무시하고 갑니다. 도착하면 Idle 이 됩니다.
  - **AttackMove**: 가면서 적을 찾아 싸우고, 대상이 죽으면 다시 목적지로 갑니다.
  - **Attack**: 지정한 적을 끝까지 쫓아갑니다. 경로는 대상이 0.5 이상 움직였을 때만 다시 찾습니다(최소 0.25초 간격).
- **선딜·쿨다운**: 사거리에 들면 멈춰서 선딜만큼 기다린 뒤 타격하거나 발사합니다. 선딜 중 대상이 사거리 + 1 밖으로 나가면 취소합니다. 플레이어 명령은 선딜을 취소합니다.
- **대상 우선순위**: 내 편을 공격 중인 적을 먼저, 같으면 가까운 순.
- **도움 요청**: 맞은 유닛 주변 8 안의, 할 일 없는 아군이 공격자를 노립니다. 이동 명령 중인 유닛은 따르지 않습니다.
- **행동 층 (전투 봇)**: 0.25초마다(유닛별로 시점을 흩어서) 판단합니다. 대상을 4초 동안 한 번도 못 치면 0.5초 동안 무시하고 다른 적을 찾고, 근처에 적이 없으면 가장 가까운 적에게 공격 이동합니다(참고 서버 `LaneMinionAI` 의 재평가 규칙).
- **사거리까지 다가가기**: 공격하러 다가가는 대상은 ORCA 이웃에서 뺍니다. 넣으면 시간 지평 때문에 가까워질수록 느려져, 근접 사거리에 닿는 데 4초가 걸렸습니다. 실제 겹침은 분리 보정이 막습니다.
- **연출**: 전투 이벤트(근접 타격·발사·사망)를 스냅샷과 같은 주기로 unreliable 로 보냅니다. 클라이언트는 그 틱이 화면에 그려지는 시각(보간 지연 반영)에 재생합니다. 이벤트를 잃어도 체력·사망은 스냅샷이 권위이므로 연출 하나가 빠질 뿐입니다.

참고 서버의 문제(`ai.md` 5장)와 대응:

| 참고 서버 | 이 프로젝트 |
| --- | --- |
| 도움 요청·공격 이동 타겟 탐색이 전체 오브젝트 순회 | 공간 격자로 범위 안만 |
| 우선순위가 같으면 순회 순서로 결정 (거리 무시) | 같으면 가까운 순 |
| 이동이 AI 판단보다 먼저 돌아 1틱 지연 | 틱 순서: AI → 전투 엔진 → 이동 → 투사체 → 사망 |
| 사거리 밖 타겟 추적 중 매 틱 A\* | 대상이 0.5 이상 움직였을 때만, 최소 0.25초 간격 |
| 봇은 플래그만 있고 AI 없음 | 전투 봇에 행동 층 AI |

### 시야 (Fog of War)

로드맵 5단계. **서버가 팀 시야 밖의 적을 아예 보내지 않는 것**이 핵심입니다. 화면만 가리면 패킷을 열어 볼 수 있으므로(맵핵), 클라이언트의 안개 막은 보조 표시일 뿐입니다.

- **시야 계산** (`Shared/Runtime/Combat/VisionGrid.cs`): 맵을 1×1 칸으로 나누고, 팀 유닛마다 시야 반지름(근접 10, 원거리 11) 안에 중심이 든 칸을 "보임"으로 표시합니다.
  - 적 유닛은 그 중심이 든 칸이 보일 때만 보입니다. 같은 팀과 중립은 항상 보입니다.
  - 벽은 시야를 가리지 않습니다.
  - 서버는 매 틱 끝에 다시 계산합니다.
  - 시야 반지름은 획득 거리보다 커서, 유닛이 보이지 않는 적을 스스로 노리는 일은 없습니다.
- **전송 필터** (`GameServer.BroadcastSnapshot`)
  - 팀마다 그 팀이 볼 수 있는 유닛만 스냅샷에 담습니다. 델타 기준도 팀별로 "그 팀에게 보낸 상태"로 따로 보관하므로, 적이 시야 밖으로 나가면 다음 델타에 제거 표시로 빠집니다.
  - 보이는 유닛이 보이지 않는 유닛을 노리면 공격 대상 ID 를 0 으로 가립니다.
  - 전투 이벤트는 공격자나 대상 위치가 보일 때만 보내고, 안 보이는 쪽 ID 는 0 으로 가립니다.
  - 지금은 팀이 둘뿐이고 사거리(7)가 시야(10)보다 짧아서, 이 두 가림은 실제로는 일어나지 않는 방어 코드입니다.
- **명령 검증**: 보이지 않는 유닛을 지정한 공격 명령은 무시합니다. ID 를 알아낸 조작 클라이언트를 막기 위한 것입니다.
- **클라이언트 안개** (`FogOfWarView`)
  - 같은 `VisionGrid` 를 내 팀 유닛의 보간 위치로 계산해 바닥 위에 반투명 막을 씌웁니다: 지금 보이는 곳 투명, 가 본 곳 반쯤, 처음 보는 곳 짙게.
  - 서버와 같은 코드라 시야 데이터를 따로 받지 않습니다.
  - 보간 지연만큼 늦게 그리므로, 안개 경계에서 적이 나타나는 순간이 막 경계와 약 0.1~0.2초 어긋날 수 있습니다.

완료 기준 확인 (`FogOfWar_EnemyOutsideVision_IsNeverInAnyPacket_AndAppearsWhenScouted`):

1. 실제 UDP 로 두 클라이언트(1팀·2팀)를 붙입니다.
2. 두 무리를 맵 양 끝으로 떨어뜨린 뒤 2초 동안 1팀 클라이언트가 받은 **모든 스냅샷 조각을 그대로 파싱**합니다. 2팀 유닛 항목은 하나도 없습니다.
3. 정찰 유닛 하나를 2팀 옆으로 보내면 2팀 유닛이 모두 보이고, 돌아오면 다시 사라집니다.
4. 마지막 상태가 서버가 그 팀에게 보낸 값과 정확히 같은지도 확인합니다.

실제 클라이언트 (`-autotest-battle` 에 시야 확인 추가: 시작 1초 뒤 받은 적 유닛 수가 0 이어야 함):

| 실행 | 결과 | 시작 직후 받은 적 | 걸린 시간 | 서버 1틱 최대 |
| --- | --- | --- | --- | --- |
| `-autotest-battle 60 open` | PASS | 0 | 43.0초 | 1.0ms |
| `-autotest-battle 200 open -latency 150 -loss 10` | PASS | 0 | 50.0초 | 3.6ms |
| `-autotest-battle 200 blocks` | PASS | 0 | 68.8초 | 9.0ms |

대역폭 (Battle 200, 1팀이 받는 양, 30초): 시야 끔 전체 30.6 KB/s · 델타 13.3 KB/s → 시야 켬 전체 27.1 KB/s · 델타 11.3 KB/s (벽 가림·안개를 지키는 봇 반영 후).

5단계 직후 남겨 두었던 과제를 이어서 처리했습니다:

| 과제 | 처리 |
| --- | --- |
| 벽이 시야를 가리지 않음 | **가림 추가.** 유닛에서 칸 중심까지 직선이 맵 벽에 걸리면 그 칸은 안 보입니다. 시야 원에 걸치는 벽만 검사하므로 벽에서 먼 유닛은 비용이 그대로이고, 클라이언트 안개도 같은 코드라 경계가 서버와 맞습니다. 건물은 시야를 가리지 않습니다. (`Walls_BlockSight`) |
| 전투 봇이 안개를 무시 | 봇은 **자기 팀에 보이는** 적만 노립니다. 안 보이면 상대 진영으로 진군하고, 거기에도 없으면 맵을 정찰합니다. "적이 아직 살아 있다" 는 사실만 압니다. |
| HUD 가 상대 팀 수를 보여 줌 | Fog of War 가 켜져 있으면 지표를 팀마다 따로 보냅니다. 상대 팀 생존 수·사망·투사체 수는 "모름"(HUD 에 `?`), 유닛 수는 그 팀이 볼 수 있는 수입니다. 겹침 지표는 디버그용이라 전체 기준 그대로입니다. |
| 안개 속 유령 없음 | **유령 추가.** 적이 시야 밖으로 나가 스냅샷에서 빠지면 마지막으로 본 자리에 어두운 원판을 남기고, 그 자리가 다시 보이면 지웁니다. 사라진 뒤 0.35초 안에 사망 이벤트가 오면 남기지 않습니다(스냅샷 제거와 사망 연출의 시점 차이). |
| 벽 있는 맵에서 1틱이 30~40ms 까지 튐 | Step 단계별 시간(`World.LastProfile`)으로 재 보니 원인이 추적 A\* 였습니다. 추적·공격 이동·막힘 재경로가 쓰는 A\* 를 **틱마다 셀 확장 12,000개**로 제한하고, 넘으면 다음 틱으로 미룹니다. 경로 하나의 비용이 수십~수천 칸으로 달라서 횟수가 아니라 확장 수로 셉니다. 플레이어 명령은 제한하지 않습니다. 그 결과 Blocks 200 의 최대 1틱이 41ms → 14ms 안팎으로 줄었습니다. Open 600 의 최대(약 20ms)는 600명이 한데 엉킨 ORCA 비용이라 경로와 무관합니다. |

### 경제 · 건설

로드맵 6단계. F2 의 `Skirm` 시나리오(또는 `--scenario skirmish`)를 고르면, 플레이어마다 자기 팀 진영에 다음을 받고 시작합니다:

- 본진
- 일꾼 4
- 맵 가장자리 쪽 반원에 광맥 8 (각 800)
- 자원 100

봇은 없습니다.

| 종류 | 비용 | 시간 | 체력 | 만드는 곳 / 역할 |
| --- | --- | --- | --- | --- |
| 일꾼 | 50 | 6초 | 40 | 본진. 채집·건설, 약한 근접 공격(4) |
| 근접 | 60 | 8초 | 120 | 병영 |
| 원거리 | 75 | 9초 | 70 | 병영 |
| 병영 | 150 | 15초 | 700 | 일꾼이 짓는다. 발판 3×3 |
| 본진 | — | — | 1500 | 시작 건물. 일꾼 생산·자원 반납. 발판 4×4 |
| 광맥 | — | — | — | 중립. 다 캐면 사라진다. 발판 1.2×1.2 |

- **채집**
  - 일꾼이 광맥 옆에서 1초 동안 5를 캐서 가장 가까운 내 본진에 반납하고, 다시 같은 광맥으로 갑니다. 광맥이 다 떨어지면 15 안의 다른 광맥으로 옮깁니다.
  - 새로 나온 일꾼은 근처 광맥으로 바로 갑니다.
  - 채집·건설 중인 일꾼은 적을 무시합니다.
- **건설**
  - 비용은 명령할 때 냅니다. 일꾼이 현장에 도착하기 전에 다른 명령을 받으면 돌려줍니다.
  - 현장은 맵 안, 우리 팀 시야 안이어야 하고, 벽·건물·광맥과 지름 2개 이상 떨어져 있어야 합니다(유닛이 지나갈 틈).
  - 도착했을 때 현장에 다른 유닛이 서 있으면 5초까지 기다리고, 그래도 막혀 있으면 포기하고 비용을 돌려줍니다.
  - 일꾼이 붙어 있는 동안만 지어지고(진행도만큼 체력도 참), 떠나면 멈춥니다. 다른 일꾼으로 우클릭하면 이어 짓습니다.
- **생산**: 건물마다 대기열 5칸, 비용은 넣을 때 냅니다. 여러 건물을 골라 생산하면 대기열이 짧은 곳에 넣습니다. 완성된 유닛은 맵 가운데 쪽 문 앞에 나옵니다.
- **건물은 장애물**
  - 건물·광맥 발판은 길찾기 격자와 RVO2 장애물에 벽처럼 들어갑니다. 생기거나 없어질 때만 다음 틱 시작에 격자를 다시 만듭니다(200×200, 수 ms).
  - 건물은 공격받을 수 있고 반격하지 않습니다. 대상 우선순위는 공격하는 유닛보다 낮습니다.
  - 부서지면 길이 다시 열립니다.
- **자원은 비밀**: 자원과 생산 대기열은 `PlayerState` 메시지로 그 플레이어에게만 보냅니다(5Hz). 남의 자원은 패킷에 없습니다.

| 조작 | 기능 |
| --- | --- |
| 우클릭 광맥 | 선택한 일꾼 채집 (다른 유닛은 그 자리로 이동) |
| 우클릭 짓다 만 내 건물 | 일꾼이 이어 짓기 |
| B → 좌클릭 | 병영 배치 (초록·빨강 미리보기, Shift 로 여러 개, 우클릭·Esc 취소) |
| Z / X | 선택한 본진에서 일꾼, 병영에서 근접 / 원거리 생산 |
| 왼쪽 아래 패널 | 자원, 선택 구성, 생산 버튼, 선택한 건물의 대기열과 진행도 |

화면: 본진·병영은 팀 색 상자(지어지는 동안 진행도만큼 낮음), 광맥은 남은 양만큼 작아지는 하늘색 수정, 일꾼은 작은 몸에 자원을 들면 등 위에 수정이 보입니다.

로드맵 6단계 완료 기준 확인:

- 서버 테스트 `EconomyFlow_WorkerProduction_Gathering_Barracks_Army`: 일꾼 4명 채집 → 본진에서 일꾼 생산 → 150 모아 일꾼 하나로 병영 건설(길찾기 격자에 장애물로 들어가는지 확인) → 완성 → 근접 유닛 생산.
- 실제 클라이언트 `-autotest-economy [map]`: 같은 흐름을 클라이언트 명령과 화면 상태(스냅샷)·서버가 보낸 자원만으로 진행합니다.

| 실행 | 결과 | 일꾼 생산 | 병영 비용 모으기 | 병영 건설 | 근접 생산 | 전체 |
| --- | --- | --- | --- | --- | --- | --- |
| `-autotest-economy open` | PASS | 6.1초 | 12.1초 | 1.1초 이동 + 15.1초 | 8.1초 | 43.7초 |
| `-autotest-economy blocks -latency 150 -loss 10` | PASS | 6.3초 | 12.7초 | 1.4초 이동 + 15.1초 | 8.3초 | 45.1초 |

| 테스트 | xUnit | 시뮬레이션 로직은 서버 프로세스 없이 단위 테스트 |

## 4. 아키텍처 계획

### 4.1 동기화 모델: 서버 권위(server-authoritative) 상태 동기화

전통적인 RTS(유닛 수백 개)는 입력만 주고받는 **결정론적 락스텝**을 많이 씁니다. 이 프로젝트는 참고 서버와 같은 **서버 권위** 방식을 택합니다.

| 항목 | 락스텝 | 서버 권위 (채택) |
| --- | --- | --- |
| 대역폭 | 입력만 보내므로 매우 적음 | 상태를 보내므로 많음 → 변경분·시야 필터링으로 줄임 |
| 결정론 요구 | 모든 클라이언트가 비트 단위로 같아야 함 (Unity float, 물리 사용 불가) | 서버만 계산하므로 불필요 |
| 맵핵 방지 | 모든 클라이언트가 전체 상태를 가짐 → 불가능 | 시야 안의 정보만 보냄 → 가능 |
| 중간 참가·재접속 | 처음부터 재시뮬레이션 필요 | 현재 스냅샷만 보내면 됨 |
| 서버 비용 | 거의 없음 (릴레이) | 서버가 시뮬레이션 수행 |

### 4.2 이동 동기화: 서버 위치 스냅샷

충돌 회피에 **RVO2(ORCA)** 를 쓰므로 유닛 속도가 매 틱 바뀝니다. 그래서 참고 서버처럼 경로(웨이포인트)를 보내고 클라이언트가 따라가게 하는 방식은 쓸 수 없습니다. 클라이언트가 그리는 위치가 서버 위치와 금방 어긋나기 때문입니다(`collision-avoidance.md` 6.4). 대신 **서버가 계산한 위치를 주기적으로 보내고, 클라이언트는 받은 위치 사이를 보간**합니다.

```text
서버 틱:  경로 탐색(A*) → 선호 속도 계산 → RVO2로 실제 속도 결정 → 위치 적분
송신:     스냅샷 = { 서버 틱, [유닛 ID, 위치, 속도(선택), 방향] ... }
클라이언트: 스냅샷 버퍼 → 약 2스냅샷 늦게 재생하며 두 스냅샷 사이 보간
```

위치를 계속 보내면 대역폭이 커지므로 다음 방식으로 줄입니다.

- **움직인 유닛만** 보냅니다. 정지한 유닛은 멈춘 순간 한 번만 보냅니다.
- **양자화**: 위치를 맵 크기 기준 고정소수 16비트, 방향을 8비트로 압축합니다.
- **델타 압축**: 클라이언트가 마지막으로 받았다고 알려준 스냅샷을 기준으로, 바뀐 필드만 보냅니다.
- **시야 필터**: 각 플레이어에게는 그 팀 시야 안의 유닛만 보냅니다.
- **우선순위**: 패킷 예산을 넘으면 화면 근처, 전투 중인 유닛을 먼저 보내고 나머지는 다음 스냅샷으로 미룹니다.
- 스냅샷 전송 주기는 시뮬레이션 틱과 분리합니다 (예: 30Hz 틱, 15~20Hz 스냅샷).
- 체력 등 스탯은 위치와 별도로 **바뀐 값만** 보냅니다 (dirty flag 기반 복제).

대략적인 예산: 시야 안에서 움직이는 유닛 200개 × 약 6바이트 × 15Hz ≈ 18KB/s. 실제 값은 4단계에서 측정합니다.

### 4.3 서버 틱 처리 순서

30Hz 고정 틱 (`SimConstants.TickRate`). 틱마다 다음 순서로 처리합니다.

```text
1. 네트워크 수신       클라이언트 명령을 큐에서 꺼냄 (명령에 클라이언트 틱 번호 포함)
2. 명령 적용           이동/공격/건설/생산 명령 검증 후 유닛에 할당
3. AI 판단            유닛별 상위 판단 (타겟 선택, 명령 생성)
4. 이동               경로상 다음 지점으로 선호 속도 계산 → RVO2로 회피 속도 결정 → 위치 적분
5. 전투·효과           공격 타이밍, 투사체, 데미지, 버프
6. 경제·생산           자원 채집, 생산 큐, 건설 진행
7. 시야 계산           팀별 시야 갱신
8. 상태 전송           스냅샷 주기면 위치 스냅샷 + 변경된 스탯을 시야 필터 거쳐 전송
```

참고 서버는 이동이 AI 판단보다 먼저 돌아 스크립트가 정한 명령이 다음 틱에 반영되는 1틱 지연이 있었습니다(`ai.md` 2.2). 여기서는 판단을 이동보다 먼저 둡니다.

### 4.5 참고 서버 분석에서 얻은 개선점

분석 문서에서 확인한 문제를 처음부터 피하도록 설계합니다.

| 참고 서버의 문제 | 이 프로젝트의 대응 |
| --- | --- |
| 겹친 뒤 위치를 순간이동으로 밀어냄. 감지 반경과 밀어내기 반경이 달라 유닛끼리 끌려감 | 반경을 하나로 통일하고 **RVO2(ORCA)** 로 겹치기 전에 속도를 조정. 위치 동기화는 서버 스냅샷으로 함(4.2) |
| ORCA의 약점: 좁은 길과 정지한 무리 앞에서 막힘 (`collision-avoidance.md` 시뮬레이션 결과) | 막힘 감지(일정 시간 진척 없음) 시 **유닛을 고려한 A\* 재경로**로 우회. 도착·정지한 유닛은 RVO 이웃에서 우선순위를 낮춰 길을 내주게 함. 3단계에서 collision-lab 시나리오로 검증 |
| 위치 보정마다 이동 패킷 전송 | 위치는 스냅샷으로만 보내므로 보정용 패킷이 따로 없음. 움직인 유닛만 델타로 전송 |
| 일부 애니메이션 패킷이 시야 필터 없이 전체에 전송됨 (안개 속 정보 노출) | 모든 서버→클라이언트 송신을 **시야 필터를 거치는 단일 경로**로만 보냄 |
| RTT 측정 없음, 요청에 타임스탬프 없음, confirm 패킷 무시 | 핸드셰이크 후 주기적 RTT 측정, 명령에 클라이언트 틱 번호 포함, 클라이언트가 받은 마지막 스냅샷 번호를 응답 (델타 기준점) |
| 서버 틱(60Hz)과 무관하게 10초마다 시간만 동기화 | 스냅샷마다 서버 틱 번호 포함, 클라이언트는 틱 기준으로 보간 |
| AI가 이동보다 늦게 돌아 1틱 지연 | 틱 순서를 판단 → 이동으로 배치 |
| 스크립트를 실행 중 Roslyn으로 컴파일 (보안·디버깅 부담) | 능력·AI는 일반 C# 코드로 서버에 컴파일해 넣고, 수치는 JSON 데이터로 분리 |

### 4.6 클라이언트 계획

- **표현 전용**: 클라이언트는 게임 판정을 하지 않고 서버 상태를 그립니다.
- 위치 스냅샷을 버퍼에 쌓고 약 2스냅샷(15Hz 기준 약 130ms) 늦게 재생하며 **두 스냅샷 사이를 보간**합니다. 스냅샷이 늦으면 마지막 속도로 짧게 외삽하고, 다음 스냅샷이 오면 부드럽게 맞춥니다.
- 내 명령에는 즉시 반응을 보여줍니다 (클릭 이펙트, 선택 유닛 방향 전환 등). 실제 이동은 서버 응답 후 시작하며, RTS 특성상 RTT 정도의 지연은 허용됩니다.
- 입력: 드래그 박스 선택, 우클릭 이동/공격, 부대 지정(Ctrl+숫자), 건설 배치.
- 카메라: 탑다운 RTS 카메라 (가장자리 스크롤, 줌).
- 안개: 서버에서 받은 시야 정보로 Fog of War 텍스처 생성.

## 6. 열린 질문

- 프로젝트 라이선스 결정 (MIT 권장 — 외부 기여와 상용 사용 모두 허용)
- 맵 표현: 지금은 벽 사각형 + 균일 격자로 충분함 (2단계에서 결정). 맵이 커지거나 사선 지형이 필요해지면 내비메시를 다시 검토
- 유닛 수 목표치 (팀당 100 / 200) — 대역폭 예산과 시야 계산 비용이 이에 따라 달라짐
- 서버 틱 30Hz가 적절한지 (전투 반응성 vs 서버 비용, 4단계에서 측정)
- 스냅샷 주기(15Hz / 20Hz)와 보간 지연 — 반응성과 대역폭의 균형. 15Hz 에서 움직이는 유닛 300개 ≈ 30 KB/s (측정값은 1장 "스냅샷 대역폭")
